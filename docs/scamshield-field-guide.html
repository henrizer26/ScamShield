01 · Orientation

What it is

ScamShield reads an SMS and tells you whether it is a scam, in words you can check for yourself.

It is built for Tanzanian SMS fraud, so its rules are written in the language the scams are actually written in — Swahili, with the mobile-money vocabulary of M-Pesa, Tigo Pesa, Airtel Money and HaloPesa. A message can be pasted in by hand, shared into the app from Messages, or caught automatically as it arrives.

Two properties matter more than any feature, and both are worth stating first because everything else follows from them.

It never leaves the phone. The manifest requests five permissions and INTERNET is not among them. The message you are checking is never uploaded, and the app works with the aeroplane mode on.

Nothing is learned. There is no model and no training. Detection is a fixed table of regular expressions with signed weights, so every verdict can be traced to the rules that produced it — and the app shows those reasons to the user rather than a bare score.

02 · Architecture

Four layers, one direction

A single Activity hosts every screen as a Navigation-component Fragment. Nothing below the UI layer knows anything about Android views, which is why the detector can be tested on a plain JVM with no emulator.

Screens

11 Fragments + 3 Activities. Splash and Onboarding run once; MainActivity then hosts Home, Analyze, History and Settings as tabs, plus the six full-screen pages of the scan and report flow.

Handover

ScanArgs + nav_graph. One Bundle carries the scam, the verdict, the score and the indicator list from screen to screen. Nav options decide what Back means.

Engine

ScamDetector + DetectionRule. Pure Java. Takes a message and a sender, returns a classification, a score and the list of reasons. No Android imports, no I/O.

Storage

DatabaseHelper + AppPrefs. SQLite for flagged messages, SharedPreferences for the handful of settings. Both local, both unencrypted, neither synced.

Background

SmsReceiver + ProtectionService. Optional and permission-gated. When on, arriving SMS runs through the same detector and raises a notification.

The rule that keeps it honest: ScamDetector is the only thing that decides risk. Every screen that paints a colour reads it back through RiskUi, so the dashboard, the history row and the verdict screen cannot disagree about how dangerous a message is.

03 · Detection engine

Five fixed stages

Every scan runs the same pipeline in ScamDetector.detect(message, sender). The order matters: the first two stages exist so that one written rule can catch every spelling a scammer tries.

  1. Normalise

    Unicode folding, accents and invisible characters stripped, lower-cased, whitespace collapsed. One spelling of a word is then enough.

    normalize() → "TUMA  PESA" becomes "tuma pesa"
  2. Canonicalise

    Undo the two tricks that defeat keyword matching: characters that look like letters, and separators pushed between them.

    canonicalize() → "P1N" and "p.i.n" and "p i n" all become "pin"
  3. Match

    Each rule runs its pre-compiled pattern over the view of the message it was written for, and reports the text that fired it. Patterns are compiled once when the table is built, so scanning never compiles a regex.

    4 views: RAW · MESSAGE · CANONICAL · SENDER
  4. Score

    Strong rules add their full weight. Supporting rules share a capped budget so noise alone cannot convict. Genuine-traffic rules subtract. Combination rules add what only appears when two signals meet.

    strong + min(weak, 30) + combinations − suppression
  5. Classify

    The bounded score meets two fixed thresholds, and comes back with the evidence that produced it — the reasons shown on screen.

    SAFE < 30 ≤ SUSPICIOUS < 60 ≤ SCAM

The four views of one message

A rule declares which prepared view it reads, because the right view differs by what is being looked for. Phone numbers and links lose their shape once characters are folded, so those rules read the message nearly as written; wording rules read the canonical view so evasion spellings collapse into one.

FieldWhat the rule seesUsed for
RAWThe body untouched, original capitals intactShouting detection
MESSAGECase-folded, spacing collapsed; digits and punctuation keptLinks, amounts, phone numbers
CANONICALLook-alikes folded back, inserted separators removedAll wording rules
SENDERThe originating address onlyRegistered sender IDs

05 · Scoring

Why a pile of small signals cannot convict

The arithmetic is deliberately blunt, and three constraints do the real work.

  • Strong rules stand alone. Anything above WEAK_RULE_WEIGHT (15) adds its full weight. A direct request for a PIN is a verdict by itself.
  • Supporting rules share a ceiling. Everything at 15 or below is capped at WEAK_SIGNAL_LIMIT (30) in total. A promotional message with a link, an amount, a phone number, urgency and a brand name is worth 64 raw — capped, it can only ever warn, never accuse.
  • Genuine wording subtracts, but only from noise. When a strong rule has fired, suppression can cancel no more than the weak score. A bank's real security advice cools a borderline message down; it cannot excuse a message that plainly asks for money.
0 – 29SAFE

Low Risk. Nothing is stored, nothing is raised.

30 – 59SUSPICIOUS

Medium Risk. Alerts, saves to history, names the category it leans toward.

60 – 100SCAM

High Risk. Alerts and names the scam type outright.

The verdict is named after the heaviest specific category. Signals filed under the generic bucket can support a verdict but never name one, so a message is only called “suspicious” in general terms when nothing specific was found.

08 · Navigation

The scan flow, and what Back means

Nine destinations live in nav_graph.xml. Home, History and Settings are tabs and draw the bottom bar; everything in the scan and report sequence is full-screen with its own back arrow, and MainActivity hides the bar for those destinations.

Analyze ──▶ Analysis Result ──▶ Scam Details
                  │                    │
                  └──────┬─────────────┘
                         ▼
                   Report Scam ──▶ Review Report ──▶ Report Sent
                                                          │
                                        popUpTo(reportScamFragment, inclusive)
                                                          ▼
                                              back lands where it began

Two navigation decisions are worth explaining, because both fix a way a user could get stuck or do harm:

  • Analysis Result has a back arrow. Without it the screen is a dead end — its two buttons both go deeper.
  • Report Sent clears the flow behind it. Nav.afterReportSent() pops up to the report form inclusively, so the system Back button cannot walk into the review screen and send the same report twice.

09 · Storage

Where data lives

Three places, and knowing which is which explains most of the app's behaviour.

1. SQLite — flagged messages

CREATE TABLE scams(
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  phone_number TEXT,
  message      TEXT,
  scam_type    TEXT,
  date_time    TEXT,      -- yyyy-MM-dd HH:mm:ss
  is_reported  INTEGER DEFAULT 0
)

Written from exactly two places: a manual scan in AnalyzeFragment, and an arriving SMS in SmsReceiver. Only messages that alert are stored — a safe message is never written down.

What is deliberately not stored is the indicator list. The table records what a message was, not why. When History opens a stored row, ScanArgs.ofStored() re-runs the detector over the saved message to rebuild the reasons. That is cheap because the engine is pure, and it means the reasons can never drift out of step with the rule table the way a stored column would the first time a rule is edited.

2. SharedPreferences — settings

AppPrefs, file ScamShieldPrefs: dark-theme choice, first-launch flag, messages-scanned counter, protection toggle. The language choice is not here — AppCompat persists that itself through the autoStoreLocales service in the manifest.

3. A Bundle — the live scan

ScanArgs defines the keys that travel between screens: the scam, the danger level, the classification, the score and the indicator list. This is the only place the indicator list exists at runtime, which is why a screen that forgets to pass it forward shows nothing.

10 · Background

Real-time protection

Off by default and gated on two permissions. ProtectionManager is the single source of truth: isActive() is true only when the user enabled it and the permissions still hold, so revoking a permission in Android settings silently disables the feature rather than leaving it half-on.

PermissionWhy it is requested
RECEIVE_SMSso SmsReceiver sees arriving messages
POST_NOTIFICATIONSto raise the risk alert
FOREGROUND_SERVICEto keep protection visibly running
FOREGROUND_SERVICE_SPECIAL_USEthe Android 14 category for it
VIBRATEalert feedback

When a message arrives, SmsReceiver reassembles multi-part SMS, drops anything WhitelistUtils recognises as service traffic, runs the same ScamDetector, and only then stores and notifies. The absence of INTERNET from that list is the point: an SMS the app reads has nowhere to go.

12 · Testing

Two corpora, on purpose

29 unit tests run on a plain JVM — no emulator, seconds not minutes — because the detector has no Android dependency. Two of the test classes measure accuracy, and they are kept separate deliberately.

ScamDetectorCorpusTestBongoCorpusTest
Sourcewritten alongside the rulescollected separately
Size20 scam + 20 genuine1,000 scam + 508 genuine
Provesno rule edit breaks a known shapehow the rules do on unseen wording
Score~1.0 by constructionP 1.000 · R 0.674 · F1 0.805

The second set is the honest number and the lower one, and the gap between them is the reason both are kept. Measured before the rules were revised against it, the same corpus scored precision 0.982 but recall 0.384 — the hand-written corpus had said everything was fine, because the rules and those messages were written by the same hand.

Quote this number carefully. The corpus carries message bodies only, with no originating address, so every sender-dependent rule sits idle in that measurement: S03_TRUSTED_SENDER_ID, C04_BRAND_MISMATCH and the sender half of R01_KNOWN_NUMBER. Real recall on a handset, where the sender is known, should be better than 0.674 — but we have not measured that, so do not claim it as a figure.

13 · Limits

What it does not catch, and why

These are scam families the rule table does not describe yet. They are gaps in coverage, not tuning problems, and being able to name them is more convincing than claiming there are none.

  • Occult and Freemason recruitment. R08_HEALER_PROMISE covers traditional healers but not this vocabulary.
  • Healer ads written without ya. The rule requires tiba ya asili; plenty of real messages just say TIBA ASILI.
  • Letter-substitution evasion. canonicalize() folds digit look-alikes and inserted separators, but not x for s — so “Xorry nipo xafari… unixaidie” passes. The same hole lets j'ina slip past a rule written for jina.
  • Landlord and new-number impersonation. No money verb, no link; the tell is a claimed relationship plus a new number, which nothing currently scores.
  • OCR is not implemented. The Screenshot option is on the Analyze screen but does nothing yet.

One caveat for anyone adding test libraries: the Gradle JVM here is Java 25. Robolectric, Mockito's inline mock maker and anything else that instruments bytecode will fail with Unsupported class file major version 69 until a Java 17 toolchain is pinned for the test task.

A note on the database: onUpgrade currently drops and recreates the table. That is fine while DATABASE_VERSION stays at 1, but bumping it will erase every saved scam.
