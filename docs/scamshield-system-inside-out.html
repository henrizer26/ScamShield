1. Executive system summary

ScamShield is an Android application that reacts to incoming SMS events, performs local rule-based text checks, classifies detected scam patterns, and warns the user through a notification. It also supports manual analysis and currently contains optional history and reporting screens.

What is technically strong

  • Manifest-registered real-time SMS receiver
  • Multipart SMS reconstruction
  • Local analysis with no cloud AI
  • Deterministic keyword/type rules
  • Matched-indicator explanations
  • High-priority warning notification
  • Manual and shared-message analysis
  • Successful debug build

What still requires completion evidence

  • Physical-device SMS lifecycle tests
  • Permission grant/denial device tests
  • Foreground-service survival tests
  • Rule calibration using labelled SMS samples
  • Removal of out-of-scope database/history/reporting UI
  • Measured one-second performance evidence
Verified build status: testDebugUnitTest, assembleDebug, and lintDebug completed successfully on 3 September 2026. Ten unit tests passed, including nine detector tests for safe, suspicious, scam, regex/context, normalization, null input, false positives, known numbers, and score bounds. Real-device SMS/service testing remains required.

2. What was promised in the strict pitch

The SRS deliberately narrows the project to six core capabilities:

  1. Request and clearly manage SMS and notification permissions.
  2. Allow the user to enable or disable real-time protection.
  3. Receive incoming SMS events while protection is enabled.
  4. Analyze locally using normalization, tokens, keywords, phrases, regex, contextual rules, and weights.
  5. Calculate a bounded score and classify SAFE, SUSPICIOUS, or SCAM.
  6. Maintain protection in the background and alert for suspicious/scam results.

The SRS explicitly excludes OCR, VPN, cloud synchronization, community blacklists, user accounts, automatic blocking, external AI, and direct telecom/TCRA integration. These scope limits protect the project from becoming too large and give the team a precise claim to defend.

Important contradiction with the current UI: the app contains history/database and guided TCRA/operator reporting features that the strict SRS calls out of scope. The screenshot/OCR option exists but only displays “unavailable.” These extras should be described as prototypes or optional extensions—not part of the pitched core.

3. Current architecture: the real incoming-SMS path

Settings switch → permissions → ProtectionManager → foreground ProtectionService

Android telephony framework
↓ SMS_RECEIVED broadcast
SmsReceiver checks ProtectionManager.isActive()
↓ reconstruct sender + multipart body + timestamp
WhitelistUtils
↓ if not ignored
ScamDetector.detect(message, sender)
↓ classification + 0–100 score + category + weighted indicators
if SUSPICIOUS/SCAM → NotificationHelper warns user

Step 1 — Android receives an SMS

The operating system, not ScamShield, receives the cellular message. Android sends the protected android.provider.Telephony.SMS_RECEIVED broadcast to registered apps that have RECEIVE_SMS permission. ScamShield declares both the permission and SmsReceiver in AndroidManifest.xml.

Because the receiver is manifest-declared, Android can start the app process to deliver the broadcast even when no ScamShield screen is visible. SMS_RECEIVED_ACTION is one of Android's exceptions to the general restrictions on manifest-declared implicit broadcasts.

Step 2 — The receiver reconstructs the message

Telephony.Sms.Intents.getMessagesFromIntent(intent) extracts one or more SmsMessage parts. The receiver takes the sender from the first part and appends every body part into one complete string. This matters because long SMS messages can arrive as multiple protocol units.

SmsMessage[] messages = Telephony.Sms.Intents.getMessagesFromIntent(intent);
StringBuilder body = new StringBuilder();
for (SmsMessage part : messages) {
    if (sender == null) sender = part.getDisplayOriginatingAddress();
    body.append(part.getMessageBody());
}

Step 3 — Service messages may be ignored

WhitelistUtils.isServiceMessage(sender, message) ignores configured service shortcodes and also considers alphanumeric sender IDs with service wording. This attempts to reduce false alerts from operators and banks.

Known risk: the current whitelist accepts every numeric sender containing 3–5 digits as a service number. A scam sent from a short code could therefore be ignored. The declared WHITELIST_PREFIXES set is unused. Whitelist rules require documented, tested sources rather than broad assumptions.

Step 4 — Local deterministic analysis

ScamDetector.detect() checks three known phone numbers and a hard-coded keyword array. If nothing matches, it returns isScam=false, type Unknown, danger Low. If a match occurs, determineScamType() chooses a type such as healer, money request, fake phone number, prize, or bank/loan and normally assigns High Risk.

Step 5 — Side effects

Every analyzed incoming message increments the SharedPreferences scan counter. Scam results are written to the local SQLite scams table, then NotificationHelper creates or reuses a high-importance notification channel and displays a vibration alert.

Privacy correction needed: SmsReceiver logs the full sender and message body with Log.d. Production builds should never log private SMS content. Remove or redact these logs before a real deployment or privacy demonstration.

optional → Details / Report screens

This path is valuable during a classroom demonstration because it does not require waiting for a real SMS. It proves that the UI and receiver share the same detector rather than maintaining different logic.

  • Paste: reads the clipboard and opens the sender/message form.
  • Manual: opens the form directly.
  • Share: Android sends selected text to MainActivity, which routes it to Analyze.
  • Read SMS Automatically: requests RECEIVE_SMS and READ_SMS.
  • Screenshot: intentionally shows that OCR is unavailable; the strict SRS excludes OCR.

A clean message is not stored. A detected scam is stored and triggers a notification even when manually analyzed.

5. Detector logic inside out

Current decision process

INPUT: message, sender

1. Normalize nulls, Unicode, case, quotes and whitespace.
2. Tokenize the normalized message.
3. Evaluate every precompiled DetectionRule once.
4. Add each matched rule's weight and explanation.
5. Apply explicit contextual-combination bonuses.
6. Bound score to 0..100.
7. Classify: 0–29 SAFE, 30–59 SUSPICIOUS, 60–100 SCAM.
8. Return class, score, strongest category, indicators and tokens.

The outcome is deterministic: identical input produces identical output while the arrays and code remain unchanged. It runs entirely on-device and makes no network request. The manifest does not request INTERNET, which strongly supports the “no external AI API” claim.

What “normalization” means in the SRS

The implemented normalization stage now:

  1. Handle null input as an empty string.
  2. Apply Unicode normalization.
  3. Convert to a stable locale-independent lowercase.
  4. Normalize spacing and punctuation.
  5. Optionally normalize Tanzanian phone-number forms.
  6. Retain both normalized text and tokens for rule evaluation.

What weighted scoring should look like

The implementation now uses rules with IDs, compiled patterns, weights, explanations, categories, and sender/message scope. Its design is:

RuleConditionExample weightExplanation
R01Known confirmed scam number70Sender/body includes confirmed number
R02Credential request: PIN/password/OTP35Requests confidential authentication data
R03Urgency phrase15Pressures immediate action
R04Money request30Requests transfer or payment
R05URL regex20Contains a link
R06Prize wording30Claims a prize or unexpected reward
score = min(100, sum(unique matched rule weights))

0–29   → SAFE
30–59  → SUSPICIOUS
60–100 → SCAM
Important: the 30/60 thresholds are now implemented, but the SRS did not prescribe their numerical values. The team must calibrate and justify them against a labeled Tanzanian SMS dataset.

Current detector limitations

  • The initial weights and 30/60 thresholds require dataset calibration.
  • Rule coverage is deliberately small and will miss unfamiliar wording.
  • Obfuscation such as inserted punctuation or unusual spelling needs dedicated normalization/rules.
  • The whitelist still requires trustworthy sources and false-negative tests.
  • Indicators are not stored with the optional history, so reopening a saved detection loses explanations.
  • The detector has nine focused unit tests, but receiver, permission and service behavior still require device tests.

8. The background-service question

This is likely to be the supervisor's hardest technical question. The implementation now deliberately uses both components: a visible foreground service represents the user's enabled protection state, while the event-driven receiver performs the short SMS analysis.

What is implemented today

The manifest receiver wakes for an SMS, while a user-started foreground ProtectionService makes the enabled state visible through an ongoing notification. The receiver checks the stored permission-gated state before reconstruction or analysis, so disabling protection stops monitoring behavior.

Why a permanent service is not automatically better

Modern Android restricts background services. Foreground services must be user-visible through an ongoing notification and have additional start/type rules. A permanent polling service would also conflict with NFR07's event-driven efficiency goal.

The implemented decision

Strict FR18 is retained: enabling the Settings switch after permission approval stores the state and starts a special-use foreground ProtectionService with an ongoing notification. SmsReceiver still performs event-driven reception and immediately returns when protection is disabled. The service never polls the inbox.

Do not claim that the AppCompat locale metadata service fulfills FR18. It is disabled metadata infrastructure for language persistence and is unrelated to SMS protection.

9. Storage and strict scope

The pitched core does not require a database. The current implementation nevertheless uses:

  • SharedPreferences: onboarding state, theme, and total scanned count.
  • SQLite: detected scam sender, message, type, date/time, and reported flag.

This enables dashboard statistics and History, but it expands privacy responsibilities and contradicts the earlier decision not to involve a database. The SRS's ERD can be treated as a logical analysis model rather than proof that persistent tables are required.

Strict-pitch recommendation: remove or disable History/report storage for the assessment build, keep only a small SharedPreferences protection Boolean, and pass each DetectionResult in memory to the notification/result UI. If history is retained, formally revise scope and privacy requirements.

13. Questions the supervisor may ask

“Where is the AI model?”

There is none, by design. The SRS commits to deterministic string analysis. The advantage is offline operation, explainability, repeatability, low latency, and no message upload. The tradeoff is that rules require careful calibration and will not understand language as broadly as a trained model.

“How does it work when the app is closed?”

Android delivers the protected SMS broadcast to the manifest receiver and can start the app process. The receiver performs short local work and posts a notification. Be precise: this is implemented through BroadcastReceiver, not through the background service promised by FR18.

“Can every app read SMS?”

No. The user must grant the dangerous SMS permission, Android enforces it, and distribution policies may impose additional restrictions. ScamShield receives SMS_RECEIVED; it is not the default SMS application.

“How do you calculate the score?”

The detector sums matched rule and contextual weights, bounds the result to 100, and exposes every contributing rule ID and point value. The result screen displays the score and classification.

“What makes SUSPICIOUS different from SCAM?”

Suspicious is the implemented 30–59 range with suggestive but incomplete evidence; Scam is the implemented 60–100 range. SAFE covers 0–29.

“Why no database?”

The pitched detection path is transient and needs no database: receive → analyze → alert. Only the protection Boolean needs small local settings storage. The current SQLite database exists for an out-of-scope history/reporting extension and should be removed from the strict build or formally added to revised requirements.

“Why not continuously scan the inbox?”

Event-driven reception is faster and more battery-efficient. Android announces a new SMS, the receiver reacts once, and no polling loop runs. This directly supports NFR07.

“What if the message contains the word ‘pesa’ but is harmless?”

The current weighted contextual rules reduce that risk: ordinary “Nimetuma pesa ya kodi” is covered by a safe unit test, while combinations such as an explicit money request plus urgency accumulate a higher score. More labeled examples are still needed for calibration.

“Does tapping Report send automatically?”

No. The current optional report flow opens the system SMS app or share sheet with prepared text. The user remains in control. It should not be described as direct TCRA API integration.
